# ゲオモバイル 在庫復活ウォッチャー

ゲオモバイル（UQ mobile 代理店）の端末ページを見張り、**在庫切れ → 在庫あり** に変わった
瞬間にスマホへプッシュ通知を送ります。

監視対象（初期設定）

| 機種 | ページ |
|---|---|
| iPhone XR (SIMフリー) | https://mvno.geo-mobile.jp/uqmobile/smartphone/iPhoneXR_simfree |
| iPhone SE2 (SIMフリー) | https://mvno.geo-mobile.jp/uqmobile/smartphone/iPhoneSE2_simfree |
| アウトレット（訳アリ品・中古未使用品）全機種・約 30 バリアント | https://mvno.geo-mobile.jp/outlet/ |

監視は 2 系統あります。

| 実行場所 | 間隔 | 動く条件 |
|---|---|---|
| GitHub Actions | 5 分ごと（混雑時 10〜30 分遅延あり） | 常時。**これが本命** |
| 手元の Mac (launchd) | 5 分ごと（遅延なし） | Mac が起動しログイン中のときだけ |

両方動かしておくと、Mac を開いている間は速く、閉じている間も取りこぼしません。
そのぶん在庫復活時に**通知が 2 通届きます**（それぞれ独立に状態を持っているため）。
1 通で良ければ Mac 側を止めてください → `./uninstall.sh`

## 通知先（ntfy）

スマホに **ntfy** アプリ（App Store / Google Play・無料・登録不要）を入れ、
自分のトピック名を購読します。トピック名は URL を知っていれば誰でも読めるため、
**リポジトリには一切含めていません。**

- ローカル実行時 … `config.local.json`（`.gitignore` 済み）から読む
- GitHub Actions 実行時 … リポジトリ Secrets の `NTFY_TOPIC` から読む

自分のトピック名を確認する：

```bash
/usr/bin/python3 -c "import json;print(json.load(open('/Users/mori/XCODE/GeoStockWatcher/config.local.json'))['ntfy']['topic'])"
```

届くかテストする：

```bash
/usr/bin/python3 /Users/mori/XCODE/GeoStockWatcher/watcher.py --test-notify
```

## GitHub Actions で 24 時間動かす

**パブリックリポジトリなら実行時間は無料無制限**です。プライベートだと無料枠
2,000 分/月に対し 5 分間隔では約 8,600 分/月かかり、まったく足りません。
トピック名は Secrets に入るのでパブリックでも漏れません。

```bash
brew install gh
gh auth login
```

```bash
cd /Users/mori/XCODE/GeoStockWatcher && gh repo create geo-stock-watcher --public --source=. --push
```

```bash
cd /Users/mori/XCODE/GeoStockWatcher && gh secret set NTFY_TOPIC --body "$(/usr/bin/python3 -c "import json;print(json.load(open('config.local.json'))['ntfy']['topic'])")"
```

登録できたら手動で 1 回動かして、通知が届くか確認します。

```bash
cd /Users/mori/XCODE/GeoStockWatcher && gh workflow run watch.yml && sleep 45 && gh run list --limit 3
```

以降は 5 分ごとに自動実行されます。実行状況は次で見られます。

```bash
cd /Users/mori/XCODE/GeoStockWatcher && gh run list --limit 10
```

### GitHub Actions 側の注意

- **定期実行は遅れます。** `*/5` と書いても混雑時は 10〜30 分後になることがあり、
  まれにスキップされます。分単位の正確さが要る場合は Google Cloud Run + Cloud Scheduler
  など別の実行場所が必要です。
- **60 日間リポジトリに動きがないと定期実行が自動停止します**（GitHub の仕様）。
  停止前に警告メールが届くので、その際は何かコミットするか、Actions 画面で再有効化します。
- 在庫状態が変わったときだけ `state.json` がコミットされます。変化がない限りコミットは
  発生しません（毎回コミットされると履歴が 5 分ごとに埋まるため、最終チェック時刻は
  `--durable-state` で保存対象から外しています）。

## 仕組み

### 在庫判定

このサイトは在庫切れのときだけ、商品ページに次のセクションを出力します。

```html
<section id="js-soldout">
  <div class="sold_title">在庫切れ</div>
  ...
</section>
```

在庫があるページにはこの要素がありません。JavaScript 実行前の HTML に含まれるため、
ブラウザを起動せずに判定できます。

### 誤通知を防ぐ仕掛け

「`js-soldout` が無い＝在庫あり」は、取得に失敗したときにも成立してしまいます。
そのため在庫ありと判定する前に、次をすべて確認します。

1. 応答が 5,000 バイト以上ある
2. `</html>` まで届いている（途中で切れていない）
3. 在庫の有無に関わらず存在する構造アンカー `id="js-bottom_section"` がある
4. `<title>` に対象機種名が入っている（別ページへの転送でないこと）

どれか一つでも欠ければ「判定不能」として扱い、通知は送りません。
判定不能や取得失敗が **6 回連続**続いた場合だけ、「監視が止まっている可能性」という
警告通知を送ります。サイト改修で静かに壊れて見逃す事故を防ぐためです。

### アウトレット（訳アリ品・中古未使用品）の監視

https://mvno.geo-mobile.jp/outlet/ は個別の商品ページとは構造がまったく違い、
1 ページに約 22 機種・30 バリアントが並びます。`config.json` で
`"type": "outlet_listing"` を指定した対象は、この一覧ページ専用の解析を通ります。

ページの中には性質の異なる 2 種類の商品区画が同居しています。

- **訳アリ品（状態C）**: 1 機種に複数の容量があり、容量ごとに在庫状態を持つ
- **中古未使用品**（例: Galaxy A25 5G）: 容量分けが無く、機種ごとに在庫状態が 1 つ

どちらも `<section class="item_wrapper">...</section>` で 1 機種ぶんを表しますが、
区画の中に `price_box_problem` という価格表があるかどうかで種別を機械的に見分けています。
**タブの場所（HTML 上の位置）では判定していません** — サイト側がタブの並びを変えても
崩れないようにするためです。

1 バリアントを 1 監視対象として扱うため、約 30 件それぞれが独立に在庫あり/切れの
状態と復活通知を持ちます。ただし表示が煩雑にならないよう、履歴HTMLの「現在の状態」
カードには出さず、専用の一覧（チップ表示）にまとめています。ログも変化があった
バリアントだけを記録し、変化なしの場合は「30件中X件が在庫あり」の要約 1 行だけ残します。

**一斉誤通知への対策**: 一覧ページのマーカー（`-soldout` というクラス名）がサイト改修で
変わると、全バリアントが同時に「在庫あり」に見えてしまいます（実際に検証で再現しました）。
これを在庫復活と誤解して 30 件同時に通知するのを防ぐため、直前まで在庫切れだった
バリアントの **7 割以上が同時に在庫ありへ変化した場合は、更新そのものを保留**します。
訳アリ品・中古未使用品は数量限定の中古在庫なので、多数の機種が一度に再入荷することは
通常考えにくいという前提に基づく判定です。この場合は「判定不能」の連続扱いになり、
6 回続けば通常どおり健全性の警告が飛びます。

在庫があってもアウトレットの購入は Cookie 付きのフォーム送信（POST）で行われ、
個別商品への直リンクは作れません。通知をタップすると一覧ページが開くので、
機種名を見つけて手動で申し込む形になります。

### 取得方法（重要）

サイトは Akamai のボット判定を入れています。実測した結果はこうです。

| リクエスト | 結果 |
|---|---|
| HTTP/2 ＋ Chrome 相当のヘッダ一式 | **200** |
| HTTP/2 ＋ User-Agent だけ | 403 |
| HTTP/1.1 ＋ Chrome 相当のヘッダ一式 | 403 |
| HTTP/1.1 ＋ Firefox UA | 403 |
| Python `urllib`（ヘッダを揃えても HTTP/1.1）| 403 |

つまり **HTTP/2 とヘッダ構成の両方が必要**です。この条件を満たせるのが
`curl --http2` なので、取得部分は `curl` に委譲しています。

この制約のため、実行場所は**送信するHTTPの中身を自分で決められる環境**に限られます。
GitHub Actions は Ubuntu の VM 上で `curl` をそのまま実行できるので問題ありません。
Cloudflare Workers / Deno Deploy のようなエッジ環境や Node.js の `fetch`（undici）は
HTTP/1.1 になったりヘッダが正規化されたりするため、403 になる可能性が高く採用していません。

`watcher.py` の `BROWSER_HEADERS` は動作確認済みの組み合わせです。むやみに削らないでください。

### 通知

ntfy.sh へ POST します。優先度は `urgent`、通知をタップすると商品ページが開きます。
日本語タイトルは ntfy のヘッダが ASCII のみのため RFC 2047 で符号化しています。
ntfy への送信が 3 回失敗した場合のみ、保険として Mac のローカル通知に切り替えます
（`config.json` の `mac_fallback_notification` で無効化可）。

## 監視が止まったことに気づく仕組み

在庫の異常を通知する仕組みと、**仕組み自体が止まったことを通知する仕組み**は別物です。
後者は自分では検知できない（死んだ側が「死にました」と言うことはできない）ので、
外部に置いています。

1. **外部のデッドマンスイッチ** — 1周ごとに `HEALTHCHECK_URL` へ ping を送ります。
   ping が途切れると、向こうのサービスから警告が届きます。GitHub とも自宅とも
   独立した場所にあるのが要点です。1つも取得できなかった周は `<URL>/fail` を
   叩くので、「動いてはいるが何も取れていない」状態も拾えます。
   URL 未設定なら何も送りません。

   ```bash
   gh secret set HEALTHCHECK_URL --body "https://hc-ping.com/<発行されたUUID>"
   ```

   ローカルにも効かせるなら `config.local.json` に `"healthcheck_url": "..."` を足します。

2. **Mac から GitHub を見張る** — ローカル実行のたびに Actions の実行記録を確認し、
   実行中が1つもなく最後の実行から6時間以上経っていたら通知します。
   Mac は多くの時間眠っていますが、この用途は数時間に一度起きれば足ります。
   CI 側では動かしません（自分の停止を自分で検知することはできないため）。

2026-08-27 に GitHub のスケジュールが23時間発火せず、12時間まったく気づけなかった
実例があります。詳細は `POSTMORTEM.md` の 4-2 を参照してください。

## 設定

`config.json`（リポジトリに入る）と `config.local.json`（入らない）と環境変数を、
この順に重ねて読みます。後のものが勝ちます。

| キー | 既定値 | 意味 |
|---|---|---|
| `ntfy.topic` | 空（別管理） | 購読するトピック名。環境変数 `NTFY_TOPIC` が優先 |
| `ntfy.server` | `https://ntfy.sh` | セルフホストする場合に変更 |
| `ntfy.token` | 空 | 認証付きサーバーを使う場合のみ |
| `targets` | XR / SE2 / アウトレット | 監視対象。`name` / `url` / `title_contains` / `type` |
| `renotify_hours` | 6 | 在庫ありが続く間、何時間おきに再通知するか |
| `health_alert_after_errors` | 6 | 何回連続で判定不能なら警告を出すか |
| `health_alert_cooldown_hours` | 12 | 警告通知の最短間隔 |
| `mac_fallback_notification` | true | ntfy 失敗時に Mac 通知へ切り替えるか |
| `healthcheck_url` | 空 | 死活監視への ping 先。環境変数 `HEALTHCHECK_URL` が優先。未設定なら送らない |
| `ci_stall_alert_after_hours` | 6 | GitHub 側が何時間止まったら警告するか（Mac 実行時のみ） |
| `ci_stall_alert_cooldown_hours` | 12 | その警告の最短間隔 |

**監視対象を増やす**には `config.json` の `targets` に追記します。同じサイトの商品ページ
なら何でも動きます。

```json
{
  "name": "iPhone 12 mini (SIMフリー)",
  "url": "https://mvno.geo-mobile.jp/uqmobile/smartphone/iPhone12mini_simfree",
  "title_contains": "iPhone 12 mini"
}
```

`title_contains` はページの `<title>` に含まれる文字列です（例：`iPhone SE 第2世代`）。
省略しても動きますが、入れておくと転送時の誤判定を防げます。

**アウトレットのような一覧ページ**を丸ごと監視したい場合は `"type": "outlet_listing"` を
指定します（詳細は[アウトレットの監視](#アウトレット訳アリ品中古未使用品の監視)を参照）。
1 件の対象設定から、ページ内の全バリアントぶんの監視対象が自動的に作られます。

```json
{
  "name": "アウトレット（訳アリ品・中古未使用品）",
  "type": "outlet_listing",
  "url": "https://mvno.geo-mobile.jp/outlet/"
}
```

このページ専用の解析ロジックなので、`geo-mobile.jp` 以外の一覧ページや、
訳アリ品・中古未使用品と異なる HTML 構造の一覧ページには使えません。

## 判定履歴を見る

`watcher.py` を実行するたびに `history.html` が作り直されます。ダブルクリックで開けます
（外部ファイルを読み込まない自己完結の HTML です）。60 秒ごとに自動再読み込みするので、
開きっぱなしにしておけば最新の状態が映ります。

```bash
open /Users/mori/XCODE/GeoStockWatcher/history.html
```

表示される内容

- **現在の状態** … 機種ごとの在庫状態と、その状態が続いている時間
- **これまでの傾向** … 在庫復活を捉えた回数、在庫があった合計時間、平均・最短の在庫時間
- **在庫があった区間** … いつ復活していつ売り切れたか、何分もったか
- **最近のチェック** … 直近 120 件の判定結果

履歴は `history.jsonl` に貯まります。`watcher.log` は肥大を防ぐため古い行を捨てますが、
`history.jsonl` は**状態が変わったときだけ**追記されるので、過去の在庫復活は消えません。
どちらも `.gitignore` 済みで、GitHub には上がりません。

HTML を作らせたくない場合は `config.json` に `"write_html_report": false` を足します。

### 履歴の出どころ

履歴HTMLは 2 つの記録を統合して表示します。

| 出どころ | 中身 |
|---|---|
| `history.jsonl` | 手元の Mac が捉えた変化（Mac が起きている間だけ） |
| `state.json` のコミット履歴 | GitHub Actions が捉えた変化（24 時間） |

CI は在庫状態が変わったときだけ `state.json` をコミットするので、その各版に入っている
「機種・状態・その状態になった時刻」を拾えば、Mac が寝ていた間の変化も復元できます。
レポート生成時に `git fetch` して最新のコミットを取り込みます。

同じ在庫復活を両方が別々の時刻で記録するため、機種ごとに時系列で並べて**直前と同じ状態の
記録は捨てています**。結果として、先に気づいた側の時刻が残ります。どちらが捉えたかは
各区間に「Mac が検知」「GitHub が検知」と表示されます。

区間の開始時刻はあくまで**検知した時刻**です。監視が途切れていた間に復活していた場合、
実際の復活はそれより早い可能性があります。

`git fetch` を毎回走らせたくない場合は `config.json` に `"fetch_ci_history": false` を足します。

### GitHub 側のチェックも履歴に出す

CI は在庫状態が変わらないと何も残しません。そのため 1 回ごとの判定は、
**ワークフローの実行記録**（GitHub API）と**コミットから復元した状態の推移**を
突き合わせて組み立てています。コミットが無い間の実行は、直前のコミットと同じ状態を
見ていたことになるからです。

公開リポジトリなので認証は要りません（未認証の上限は 60 回/時、こちらの使用は約 12 回/時）。
止めたい場合は `config.json` に `"fetch_ci_runs": false` を足します。

状態の変化を記録できるのは実行中の CI だけなので、遷移の時刻は必ずどれかの実行の最中に
入ります。開始時刻だけで引くと変化を見つけた当の実行が「変化前」の状態を見たことに
なってしまうため、その実行が終わるあたり（次の実行の直前まで）を含めて引いています。

### 定期実行の実測間隔

`*/5` と設定していても、GitHub 側で大幅に間引かれます。実測値は履歴HTMLの
「最近のチェック」欄に表示されます。

```
実測: 中央値 60分 / 最長 3時間30分（16.9時間で 15 回。5分間隔なら 203 回のはず）
```

この間隔では、49 分で売り切れた前回のような復活を取りこぼします。そのため
**1 回の実行を長く回して隙間を自分で埋める**方式にしています。

### 内部ループ方式

1 回の実行が約 5.5 時間（330 分）ループし、**2 分ごと**にチェックします。
GitHub ホストランナーは 1 ジョブ最大 6 時間のため、その手前で切っている。
実行トリガーは間引かれても数十分〜1 時間おきには来るため、5.5 時間走っていれば
次のトリガーがほぼ確実に待機列に入り、現在の実行が終わった瞬間に始まる。

50 分ループで実測したところ、実行の終わり際に次のトリガーが待機していないと
そこで空白ができていた（カバー率 68%）。5.5 時間に延ばしたのはこの空白を
無くすため。ただしランナーをほぼ常時占有することになるので、
[POSTMORTEM.md](POSTMORTEM.md) に書いた利用規約上のグレーさは強まる。

- 在庫状態が変わったら**その場でコミット**します。ループの最後にまとめてではないので、
  実行が打ち切られても記録が残ります
- 一時的な取得失敗ではループを止めません
- 実行が重ならないよう `concurrency` で直列化しています。走っている間に来た分は待機し、
  現在の実行が終わり次第すぐ始まるため、結果的に連鎖して隙間が埋まります

パブリックリポジトリなので実行時間の課金はありません。ただし Actions を長時間回し続ける
運用は GitHub の利用規約上グレーゾーンです。停止させられた場合は実行場所を移してください。

手動実行では `loop`（既定）のほか `once` / `test-notify` / `force-notify` を選べ、
ループ分数も指定できます。動作確認は短いループが便利です。

```bash
gh workflow run watch.yml -f mode=loop -f loop_minutes=3
```

履歴HTMLの「最近のチェック」には、実行ごとに監視した範囲
（`19:16〜翌01:16 を約 330 分間、2 分ごとに監視`）と、実行中のものは`監視中`と表示されます。
また直近の期間のうち何割を監視できていたかも表示されます。
